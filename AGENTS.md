# AGENTS.md — VillaDonq V3

Laravel 10 + Inertia.js + Svelte 4 + Vite + Tailwind CSS. School management app (matrícula, pagos, estados de cuenta, profesores/materias/planes de evaluación). UI and routes are in **Spanish**.

## Commands

```bash
composer install          # PHP deps
yarn install              # Node deps (yarn, NOT npm)
php artisan key:generate  # after copying .env
yarn run build            # production assets (Vite)
yarn run dev              # dev with HMR
php artisan serve         # http://localhost:8000
php artisan migrate       # MySQL DB (named `villadonq`, root/no password)
vendor/bin/phpunit        # or: php artisan test
```

Only smoke `ExampleTest`s exist — don't assume a covered test suite. Run `vendor/bin/phpunit --filter <name>` for a single test.

## Architecture

- **Inertia + Svelte, not Blade**: pages are `.svelte` files in `resources/js/Pages/`. Controllers return `Inertia::render('Dashboard/Xyz', ...)`.
- **Layout**: `resources/js/app.js` applies `DashboardLayout.svelte` when the page name starts with `Dashboard`. New dashboard pages must live under `Pages/Dashboard/`.
- **Entrypoints** (Vite inputs): `resources/css/app.css`, `resources/js/app.js`.
- **Routes**: `routes/web.php`, all behind `auth` + `role` middleware (see `CheckRole.php`). Roles = `administrator`, `representative`, `teacher` (mapped via `App\Enums\UserTypeEnum`, values 1/2/3).
- **Business logic lives in Services**, not controllers: `app/Services/*Service.php` (PaymentService, BalanceService, StudentService, AccountStatementService, UserService, TeacherService, etc.). Controllers are thin.
- **Modules** (`Dashboard/` pages ↔ controllers): Pagos, Matricula (Student), EstadosDeCuenta (AccountStatement), Personal (User), Configuracion (MainConfig), Profesores, Materias, PlanesEvaluacion, MisPagos (Representative), MisEstudiantes (StudentGrade), Secciones, Horarios (Schedule, admin), MiHorario (MySchedule, teacher).

## Payments / Balances (core, non-obvious)

- **Payments are soft-deleted via a `status` column, NOT Eloquent SoftDeletes**: `status = 1` active, `status = 0` deleted. Deletion/update sets `deleted_by` (auth user id). `Payment::update()` actually reverts balances, soft-deletes the old payment, and **creates a new payment**.
- `PaymentObserver` (registered in `AppServiceProvider`) writes a `PaymentHistory` row on create/update/delete — side effects to keep in mind.
- **Debt model**: `BalanceStudent` holds debt as *negative* fields: `inscription` + `january`..`december`. Negative = owed; positive = overpaid. One balance per student per `school_lapse_id`.
- `BalancePayment` records which payment covered which portion (month or `is_inscription`).
- **School-year month order** (current month index is resolved against this): `september → october → … → december → january → … → august`. Status per period comes from `BalanceStudentStatusEnum` (`pending`, `paid`, `debt`, `partially_paid`) computed in `BalanceService::determineMonthStatus()` using `MainConfig` monthly price, `day_of_monthly_payment`, and grace.

## Gotchas

- **Schedules (Horarios, admin-only)**: tables `schedules` (school_lapse_id, course_id, section_id, recess_start 24h `HH:MM`, recess_duration_minutes, unique combo) + `schedule_classes` (schedule_id, day 1-5, start_time/end_time 24h `HH:MM:SS`, matter_id, teacher_id, order). Data via `ScheduleService`; controller returns `Dashboard/Horarios` with `data.periods/courses/sections/course_sections/matters/teachers/filters/schedule/occupancy` (schedule ghost = `{days: {1:[]..5:[]}, recess_*}`). UI keeps `viewMode` `"grid"` (default weekly matrix per section) vs `"form"` (edit); `reload()` does NOT use `preserveState` (removing it was required so section/period/course switches re-mount with fresh props — with `preserveState` the `data` prop never re-renders and grid stays stale). The grid is rendered by the **reusable** `resources/js/components/ScheduleWeekGrid.svelte` (prop `schedule` = `{days:{1..5:[{start_time,end_time,matter_id,matter_name,teacher_name?,section_name?,course_name?}]}, recess_start, recess_duration_minutes}`), also used by **MiHorario** (teacher; builds a `schedule` from `data.days`, no recess) and **HorarioHijo** (representative, `data.schedule`). It draws 5 weekday columns with **`position:absolute` class boxes** at `top=(hours+min/60-7)*70`, `height=top(end)-top(start)` (70px/hour, 7am baseline, NO time column) — each box shows time range + subject (bold) + teacher/section/course meta, pastel per subject, with an absolute recess band; empty state when `!hasGridContent()`. Matter colors index `MATTER_PASTELS` by `id-1` (NOT modulo) so each subject is unique (14 pastels). Below the admin grid a reactive `subjectHours` block lists each subject with total weekly hours (`Xh Ym`) sorted desc (hidden when the section has no classes). UI stores 12h selects and converts via `to24String`/`from24String` helpers. Recess applies to all weekdays.
- **My Schedule (MiHorario, teacher-only read-only)**: `MyScheduleController@index` → `Dashboard/MiHorario`. `MyScheduleService::getIndexData(teacherId, lapse?)` lists ALL classes where that `teacher_id` has `schedule_classes` in the period (lapse `status 1` by default), grouped by day and each tagged with `course_name`/`section_name`; teacher field is omitted (it's the logged-in teacher). No course/section filter — the teacher sees their whole week, and each class card shows the section as read-only text. Teacher nav link `/dashboard/mi-horario`. Only query param is `school_lapse_id`.
- Test env (`phpunit.xml`) uses `array` cache/mail and `sync` queue. SQLite is **commented out**; uncomment `DB_CONNECTION=sqlite` + `DB_DATABASE=:memory:` to run tests against SQLite instead of needing MySQL.
- `configure-scheduler.php` (repo root) sets up a platform scheduler (cron / Windows `schtasks`) to run `artisan schedule:run` every minute — touch it only to inspect scheduler wiring.
- Route ↔ page naming is Spanish and not always obvious: e.g. route `/dashboard/estados-de-cuenta` renders `EstadosDeCuenta.svelte`, `/dashboard/pagos` → `Pagos.svelte`.
- `Personal.svelte`, `Pagos.svelte`, `MisPagos.svelte` are large, frequently-edited pages.
- **Evaluation plans (Planes de evaluación, teacher `MisPlanes` + admin `PlanesEvaluacion`)**: frontend uses a "units → topics" model, but `EvaluationPlanService` flattens them into rows of `evaluation_plan_items` carrying `unit_name`, `unit_number`, `assessment_type`, `points`, `scheduled_date`, `description` (plus `name`, `percentage`, `date`, `order`). These extra columns were added by migration `2026_08_30_224015_...` (the base create migration only had `evaluation_plan_id/name/percentage/date/order`) — the `EvaluationPlanItem` model `$fillable` lists all of them. If a fresh DB still fails with `Unknown column 'unit_name'`, run `php artisan migrate`.
- **Teacher `MisPlanes` filtering**: the Plan/Materia table has NO "Período"/"Momento" columns — those are two `<select>` filters above the table ("Período escolar" = single-select, no "Todos", defaults by date; "Momento" = "Todos" + lapses of the selected period). Server-side filtering lives in `EvaluationPlanService::getPlansForTeacher($teacherId, $filters)` reading `school_lapse_id`/`lapse_id`/`matter_id`; if `school_lapse_id` is absent it defaults to `currentSchoolLapseId()` (the school lapse whose moments' `start`..`end` span contains today, falling back to `status=1` then the most recent). Controller returns `data` + a `filters` prop. Changing the período resets `lapse_id`. There's also a "Materia" filter (default "Todas", options = teacher's `data.matters`). The admin `PlanesEvaluacion` uses the reusable `Search.svelte` component (top-right bar, query param `search`, matches name/description/materia/course/section/school lapse/teacher in `getPlansForAdmin`) plus a filter bar with Período escolar / Momento / Año (`course_id`) / Sección (`section_id`) selects (Momento = lapses of the selected período, resets on período change; Año/Sección default "Todos" — the old Materia/Profesor filters were removed). Search and selects persist each other: `Search.svelte` gained an optional `extraSearchParams` prop (default `{}`, backward-compatible — other pages unaffected) that merges the current select-filter values into the debounced search `router.get` so typing in search keeps the applied selects; the selects' `applyFilter`/`buildParams` in turn preserve `filters.search`. It still shows Período/Momento columns; its `plan` cell is styled like MisPlanes (bold name + truncated description). **Note**: the school lapse payload item has only `id`/`label`/`is_active`/`lapses` — its own `start`/`end` are NOT exposed; only the moments (`lapses[]`) have `start`/`end`. Default-by-date logic uses those moment ranges. Also: `formatPlan` returns a `plan.units` array (`[{unit_number, name, topics:[{name, assessment_type, description, percentage, points, scheduled_date}]}]`); the read-only "Ver plan" modal renders those units→topics.
- **MisPlanes topic-date reminder**: when the teacher picks a topic's `scheduled_date`, `EvaluationPlanService::getAllowedWeekdays(array $params)` (exposed via `GET /dashboard/mis-planes/allowed-days`) returns `{restrict, allowedWeekdays}` by querying `Schedule` for `school_lapse_id`+selected `course_id`+`section_ids`, then unioning the `day` (1-5) of `schedule_classes` where `matter_id` AND `teacher_id` match the logged-in teacher; `restrict` is true only if a schedule exists and the union is non-empty (verified for Biología 5to Año A → `[1,2]`). The frontend (MisPlanes.svelte) keeps the **native `<input type="date">` and, when `allowedWeekdays` is non-empty, clicking the input opens a **floating amber tooltip** above it: "Recuerda: para esta materia {en esta sección / en todas las secciones} das clases los días {lunes} y {martes}." (closes on outside click; does NOT restrict/block any dates). Typing in the input works normally. The input's `on:click` AND `on:focus` call the `openCalendar(el)` helper (a shared `showPicker()` wrapped in try/catch, debounced via a 300ms `lastShowPickerAt` guard so focus+click on the same gesture doesn't double-open) to force the native calendar popup to open even when the user clicks directly on the day/month/year segments or tabs into the field; browsers without `showPicker` just keep the default typing behavior. `allowedWeekdays` is fetched (debounced 250ms) via `fetch()` whenever the form's `school_lapse_id`/`course_id`/`matter_id`/`section` selection changes while the form modal is open; a `TopicDatePicker.svelte` component implementing date restriction via `@svelte-plugins/datepicker` was built then **removed** (that lib caches its calendar so day-cell classes go stale unless the component is remounted).
- **Admin `PlanesEvaluacion` swipe/approve flow**: approving (`/planes-evaluacion/{id}/aprobar`) or rejecting (`/rechazar`, needs `admin_note`) a plan while the Estado filter is "Pendiente" auto-advances the modal to the **next pending plan** (no extra click). **Server-driven, not onMount**: Inertia preserves the component instance across the 302 redirect after `router.post`, so `onMount` does NOT re-run — instead the controller's `redirectBackToPlans()` (which preserves filter query params) flashes a one-time `open_plan` (the client-sent `next_plan` input) into `filters.open_plan` via `session()->pull`, and a `$:` reactive block (`if (filters.open_plan && currentPlanId !== Number(filters.open_plan))`) finds that plan in `data.plans` and calls `openPlanFor(target)`. `openPlanFor()` rebuilds `pendingQueue = data.plans.filter(status==="pending")`, sets `currentPlanId`/`currentQueueIndex`, resets reject state, and opens the modal. **Both** the filter-row click (SelectableRow `on:select`) and the "Ver plan" button route through `openPlanFor` so `pendingQueue` is always populated (the original bug: opening via row-click left `pendingQueue` empty → `next_plan` was sent as `null` and no auto-advance). `nextPlanId(id)` returns the next pending id in the queue only when `effectiveStatus === "pending"`, else null; the approve/reject POST sends `{...buildParams(), next_plan: nextPlanId(id), [admin_note]}` and, when `next` is null (last pending), `onSuccess` closes the modal with `showModal = false` (the Modal component stays mounted but becomes `opacity-0 pointer-events-none`). A counter (`Plan X de Y (pendiente)`, only when `pendingQueue.length > 1`) + a manual "Siguiente ›" button navigate the queue client-side. The plan content (heading + `PlanUnitsView` + action buttons) is wrapped in `{#key plan.id}` with `in:fly={{y:10,duration:180}}`/`out:fade={{duration:120}}` so switching plans plays a brief slide-in transition that signals the plan changed.
